## Selected implementation: Speed / Intave Boat

The current evaluator grants collision tolerance around boats instead of requiring exact ordinary movement simulation:

- [`LazyEntityCollisionService`](https://github.com/intave/intave/blob/4f18a06dce4066fa433d44cdd637472a928a73b0/src/main/java/de/jpx3/intave/module/tracker/entity/LazyEntityCollisionService.java#L26) refreshes the nearest boat on Bukkit movement events. Acquisition distance is `1.5 * 1.2 = 1.8` blocks from the verified player position. The modern happy-ghast surface path does not apply to a 1.8.9 client.
- [`MovementMetadata.collidedWithEntity`](https://github.com/intave/intave/blob/4f18a06dce4066fa433d44cdd637472a928a73b0/src/main/java/de/jpx3/intave/user/meta/MovementMetadata.java#L526) uses a cached boat position within two blocks.
- [`DefaultSimulationEvaluator`](https://github.com/intave/intave/blob/4f18a06dce4066fa433d44cdd637472a928a73b0/src/main/java/de/jpx3/intave/check/movement/physics/evaluation/DefaultSimulationEvaluator.java#L525) raises each horizontal-axis tolerance to at least `0.4` in that state; uncovered horizontal deviation is calculated after subtracting these tolerances.
- [`Physics`](https://github.com/intave/intave/blob/4f18a06dce4066fa433d44cdd637472a928a73b0/src/main/java/de/jpx3/intave/check/movement/Physics.java#L459) does not add horizontal error to its accumulated offset when horizontal violation increase is below `0.1`. Its separate velocity comparison also excludes the boat-collision state.
- [`Physics.endMovement`](https://github.com/intave/intave/blob/4f18a06dce4066fa433d44cdd637472a928a73b0/src/main/java/de/jpx3/intave/check/movement/Physics.java#L257) builds subsequent post-tick motion candidates from sent offset motion. Inference: accepted additional horizontal motion becomes part of the next simulation baseline; simply resuming vanilla drag on exit is preferable to subtracting a remembered client impulse.

This is a concrete gap between strict simulation and a broad environment allowance. The implementation is deliberately limited to that environment. It does not provide general speed away from boats. The client cannot observe Intave's actual cached boat state; warm-up and spatial margin only reduce this uncertainty.

The additional acceleration is injected through `PlayerMoveUpdateEvent.friction`, at the final consumer inside vanilla `Entity.moveFlying`, in the same physical step. It runs after every event listener and after the existing rotation correction, so prediction uses the actual final inputs. No timer, movement packet, position, vertical velocity or existing horizontal velocity is overwritten. The increment is `0.035` with a predicted horizontal displacement cap of `0.4` blocks per tick. These are client experiment limits, not claimed universal anticheat thresholds.

Activation requires six consecutive ordinary player ticks near the same registered, live, stationary boat. Previous, current and predicted player positions must each be within 1.5 blocks of it. Sprinting forward on a flat, fully supported surface is required; jumping, using an item, liquid, a ladder, collision/ledge, damage, GUI, loss of focus or an invalid scene stops additional acceleration. Extra steps cannot stack it. Applied knockback, explosion impulse and position correction pause the experiment, then require fresh warm-up. The optional module suffix reports warm-up or the current exclusion reason. Disable and setting changes clear this state.

This deliberately small region can give only one boosted step in a straight pass alongside one boat. It is a test of a specific tolerance gap, not general faster travel across an arbitrary map.

Scalar source-model comparison, not execution of Intave: with forward input `0.98`, the additional straight-line displacement is approximately `0.98 * 0.035 = 0.0343`. If no other allowances apply, the evaluator's initial horizontal-axis tolerance of `0.0007` leaves approximately `0.0336` uncovered; the boat allowance of `0.4` leaves zero for that same axis. This explains why the environment gate matters. It does not reproduce simulation search, cached state, other checks or a server decision.

## User server comparison

1. Record the actual server Intave build/config and whether cloud detection is active. The source revision above may differ from a deployed build.
2. Use a flat solid floor and a stationary boat. Start with only Speed enabled; choose `Intave Boat`. Disable timer, Tickbase, LagRange, NoSlow and Velocity changes for this comparison.
3. Warm up while moving slowly near the same boat for at least six ordinary ticks, then sprint along its side without jumping. Stay within the client's range gate; an ordinary entity or a distant boat must not activate it. A row of spaced boats can extend the route, but changing the selected boat requires fresh warm-up.
4. Compare identical passes with Speed disabled and enabled. Record effective distance/time, packet rate, vertical trajectory, setbacks, client input response and the server's check logs if available. A short client speed increase alone is not a successful bypass.
5. Repeat the exit, boat removal/movement, damage/knockback, position correction, GUI, reconnect and disable cases. Stop attribution if another movement module or external impulse changes the route.
6. Mark acceptance pending until the server applies the additional displacement without mitigation. Keep the PR Draft until that gameplay gate has been reviewed.
